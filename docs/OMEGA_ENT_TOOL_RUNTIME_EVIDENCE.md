## Implementacja
- graph-runner.mjs: walidacja grafu (do 256 nodes, 4096 edges), zależności i jawnego porządku, zaufany rejestr handlerów, sekwencyjne wykonanie, tylko wyniki bezpośrednich zależności przekazywane handlerowi, JSON budget domyślnie 1 MiB, deadline domyślnie 60 s, limit per node, AbortSignal i fail-fast. Timery utrzymują pętlę event loop i są czyszczone. Timeout zatrzymuje orkiestrację; handler musi respektować sygnał, inaczej może działać dalej. Brak distributed fencing, trwałego execution replay, dynamicznego planera, per-tenant quota i równoległego DAG.
- search-gateway.mjs: Tavily research i Exa technical przez stałe HTTPS API, SearXNG privacy z zaufanego endpointu operatora. Tylko publiczna treść, bez niezaufanych URL w request, redirect:error, timeout 10 s, max 1 MiB odpowiedzi, max 5 wyników, HTTP(S) URL i oznaczenie untrusted; brak automatycznego fetchowania linków. Nie gwarantuje ZDR, DLP ani pełnego SSRF firewallu: operator musi zabezpieczyć zaufane endpointy/DNS/egress. Wymaga zaufanego klasyfikatora. Dokumentacja kontraktów: https://help.tavily.com/articles/4840311948-tavily-search-api ; https://docs.searxng.org/dev/search_api.html ; Exa https://api.exa.ai/search . Serper, MCP transport i livecrawl nie zaimplementowane. Provider responses modelowane.
- gvisor.mjs: adapter Linux /usr/bin/docker execFile (bez shell interpolation), własny unix socket, tylko operator-pinned digest i --pull=never, --runtime=runsc, sieć none, readonly root, cap-drop ALL, no-new-privileges, UID/GID 65534, 1 CPU, 256 MiB, 64 PID, tmpfs /tmp, input max 64 KiB, stdout/stderr maxBuffer 256 KiB, start limit 30 s. Inspekcja wybranych właściwości przed startem i terminalnego exit status 0 bez OOM po starcie; cleanup w finally, niepowodzenie widoczne. Brak fallback do hosta, GPU i Firecracker. Wymaga dedykowanego, operator-owned hosta z zaufanym obrazem i daemonem, nie udostępniać Docker socket modelowi. Brak pełnej weryfikacji wszystkich pól Docker inspect, hardeningu daemon/host, reaper po awarii procesu, distributed limits, testu faktycznego runsc i barier izolacji. Polecenia Docker testowane z deterministycznym adapterem. Weryfikacja dokumentacji: https://gvisor.dev/docs/user_guide/quick_start/docker/ ; https://docs.docker.com/engine/storage/tmpfs ; https://docs.docker.com/reference/cli/docker/container/start .
- agent-runtime.mjs: kompozycja w procesie, AIM.check scope assign_tasks z tenant/agent, per-tool permission literal allow (deny/ask nie wykonuje), zaufany klasyfikator ustawiający classification, wejściowy snapshot i limit 1 MiB. Wyłącznie web_search_plus i sandbox_execute; nie umożliwia arbitralnej rejestracji narzędzi przez użytkownika. Adaptery permission/classification muszą pochodzić z zaufanego hosta, nie z LLM. Brak implementacji live Permit Tool policy, trwałej akceptacji ask, publicznego endpointu, połączenia z Temporal Worker, zautomatyzowanego sklejania wyników w argumenty kolejnych narzędzi. AIM/policy/classification w tym zestawie testowane z doubles, nie z realnymi usługami. AbortSignal nie gwarantuje przerwania rozpoczętej operacji i nie daje exactly-once.
