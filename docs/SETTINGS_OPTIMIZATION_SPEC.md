# Locally Uncensored — Integrated Settings & Resource Optimization
Data: 2026-11-20. Przyrost wymagań z raportu operatora „Kompleksowa Analiza i Optymalizacja Ustawień w Środowisku Locally Uncensored”. Dokument nie potwierdza wszystkich twierdzeń raportu ani możliwości upstream; źródło przypięte w repozytorium pozostaje podstawą audytu. Nie usuwa wcześniejszych wymagań Enterprise.

## 1. Ustawienia i sprzęt (ENT-12, ENT-31)
- Jeden panel Settings/Integrated App: lokalne i zdalne silniki, obsługiwane możliwości, adresy i porty; wykrywanie i konfiguracja Ollama, LM Studio, vLLM, llama.cpp, KoboldCpp oraz ComfyUI. Inni dostawcy jako rozszerzalne adaptery, nie deklarowana liczba bez audytu. Klucze w Keystore/credential vault, nie w localStorage ani logach; explicit opt-in chmury, failover nie może wysłać lokalnych lub prywatnych danych bez zgody.
- ComfyUI: domyślny port 8188 jako kandydat, start/stop/restart wyłącznie instancji zarządzanych przez aplikację; wykrywanie istniejącego serwera, konfliktów portów, ścieżek i wersji. Nie zabijać obcych procesów; endpointy użytkownika sprawdzać i chronić przed SSRF.
- Model Storage: własne ścieżki GGUF, native browse/reset, wolne miejsce, NAS i dyski lokalne, SAF Android, wznowienie pobierania, sumy kontrolne i weryfikacja licencji. Instalacja modeli wieloplikowych transakcyjna; brak automatycznego wykonywania pobranego kodu lub custom nodes. CivitAI/Hugging Face jako źródła po zatwierdzeniu operatora.
- Single instance i ponowne uruchomienie onboardingu bez usuwania ustawień; trwałe memory i RAG; wybór PL/EN STT/TTS. Dla Androida istniejący OmegaThermalMonitor i Resource Arbiter muszą zostać połączone z dopuszczeniem zadań; brak drugiego APK.
- Profilowanie zasobów: RAM, VRAM lub pamięć zunifikowana, wolne miejsce, backend CPU/CUDA/Metal/Vulkan/OpenCL/NPU, temperatury, szybkość, możliwości offloadu; osobne wymagania dla inferencji, treningu, obrazu i wideo. Nie zakładać równoważności pamięci dedykowanej i zunifikowanej ani że obecność CPU/GPU oznacza kompatybilność modelu. Wszystkie wymagania sprzętowe zależą od kwantyzacji, rozmiaru/sposobu alokacji kontekstu, KV-cache, batch, workspace, komponentów wizualnych i opcji offload. Model MoE nadal wymaga uwzględnienia wszystkich rezydentnych wag, nie tylko aktywnych ekspertów.
- Keep-alive/presety oszczędzania: dynamiczna rezydencja wag zależna od obciążenia, nie ustawienie 24h wymuszane globalnie. Użytkownik może wybrać zachowanie, ale scheduler musi mieć prawo zwolnienia własnego modelu zgodnie z rezerwacją i bezpieczeństwem. Unload wyłącznie po sprawdzeniu własności instancji i aktywnych zadań.
- OOM: świadome zmniejszanie kontekstu/batch/rozdzielczości/liczby klatek lub wybór kompatybilnej kwantyzacji; diagnostyka błędów, jawne retry, brak niejawnego zmieniania jakości i wyłączania zabezpieczeń OS. Blokować przy braku wymaganej pojemności, zamiast obiecywać konkretne t/s. Narzut Tauri, rozmiar instalatora i wydajność CPU/GPU wymagają pomiarów.
- Model Manager: proponowani kandydaci raportu (Qwen 3.6 dense/MoE, Gemma 4 E2B/E4B/26B/31B, Llama 3.1 8B, Hermes, Dolphin, GLM 5.1, Qwen Coder oraz warianty GGUF) mają być zweryfikowani na podstawie model cards i możliwości backendu. Nie traktować podanych rozmiarów, licencji, token/s, kontekstu i dostępności kwantyzacji jako potwierdzonych. Warianty modyfikowanych wag wymagają legalnego pochodzenia, wersjonowania, ewaluacji jakości i bezpieczeństwa; system narzędzi egzekwuje uprawnienia niezależnie od zachowania LLM.

## 2. Profile sampling (ENT-12, ENT-31, ENT-21)
Wartości startowe z raportu, nie uniwersalne ustawienia: coding/analityka temperature 0.1–0.3; creative 0.7–0.85; top-p, min-p, repetition penalty, Mirostat, seed, context length, max output, batch i think/explanation budget. Każde pole walidowane względem konkretnego API i model card. Sampling nie daje gwarancji poprawności kodu ani deterministycznego wykonania. Thinking Mode ma pokazywać obserwowalne etapy narzędzi, uzasadnienia i źródła, nie wymuszać prywatnych łańcuchów myślowych. Gdy backend nie obsługuje parametru, jasno rozpoznawać capability/error; nie przesyłać go automatycznie ani nie deklarować arbitralnej minimalnej wersji. Preset modelu może nadpisywać zakres globalny. Tokenizer, chat template, output reserve i chroniony kontekst zgodne z ENT-15.

## 3. ComfyUI (ENT-32)
- Pobranie /object_info, walidacja typów slotów i połączeń, schemat węzła, wersje i capabilities; graf generowany dla konkretnej architektury. Dynamic workflow nie oznacza zaufania do dowolnego custom node. Węzły nieautoryzowane blokowane; pliki i ścieżki odseparowane.
- Image: SDXL/FLUX/Z-Image Turbo jako rodziny do profilowania zgodnie z modelem i jego schedulerem; rozdzielczość/bucket, sampler (Euler/DPM++ 2M), steps, guidance/CFG, negative prompt tylko jeśli wspierany, seed, upscaler i tile settings. Raport podaje 25–30 steps jako punkt startowy dla części modeli, 5 dla określonego turbo, CFG 4–6 dla części SDXL i 1024² jako popularny poziom bazowy; nie stosować tych samych liczb bezwarunkowo do FLUX/distilled.
- Img2Img: denoise 0.1–0.3 retusz zachowawczy, 0.4–0.6 transfer umiarkowany, 0.7–1 silna zmiana jako orientacyjne zakresy. Nie interpretować denoise jako gwarantowanego procentu zachowania obrazu/tożsamości. Podgląd, nieodwracalność edycji niedopuszczalna, założenia o prawach i zgodzie na użycie materiału źródłowego.
- Video: Wan 2.1 1.3B/14B oraz HunyuanVideo jako kandydaci do model-specific bundles; osobna walidacja komponentów, VAE/encoder, wariantu I2V/T2V, dtype, frames, batch, fps, scheduler i rozdzielczości. Ustawienia 480p/720p i 30–40 steps z raportu traktować jako profile eksperymentów, nie wymagania per frame dla każdego modelu. Dobór liczby kroków zgodny z architekturą; ocena stabilności temporalnej i ruchu.
- Odtwarzanie kompozycji: zapisać seed, dokładny workflow, model hashes, runtime i wersje węzłów, parametry oraz wymiary. Nie obiecywać bitowej powtarzalności na różnych urządzeniach, sterownikach lub wersjach.
- Diagnostyka: OOM, niedostępny węzeł, niezgodny VAE/encoder, zmiana API, błędy pobierania HF/404, brak storage i konflikt portu. Nie zalecać wyłączania skanera antywirusowego zamiast podpisu i weryfikacji.

## 4. Uprawnienia (ENT-06/07/09/10/11)
Trzy tryby deny/ask/allow; ask musi prowadzić do rzeczywistego, ograniczonego zatwierdzenia, nie cichego allow. Bazowe kategorie planowane: pliki, shell/exec, search/egress, narzędzia MCP, pamięć/dane, urządzenia, operacje finansowe. Dokładna zgodność z siedmioma kategoriami i liczbą narzędzi upstream wymaga audytu, nie zakładać liczby z raportu. Zaufane scope i per-tool policy na serwerze; izolacja repozytoriów i tenantów, brak arbitralnej powłoki hosta. Lokalność nie gwarantuje zgodności z RODO ani braku transferu, zwłaszcza przy zewnętrznych providerach. 

## 5. Kryteria odbioru
ENT-31/32: schema/capability contracts, walidacja ustawień, testy negatywne i graniczne, testy konfliktów i rollback, rzeczywiste odpytywanie modeli/backendów, pełny build interfejsu, pomiary RAM/VRAM/TTFT/tokens/s/frame time na opisanej konfiguracji, termika, energia, odzyskiwanie po OOM, powtarzalność artefaktów. Testy symulowane i fizyczne raportować oddzielnie; przykładowe wartości nie zastępują danych pomiarowych. Żadnego automatycznego wydawania środków ani uruchamiania płatnych runnerów.
